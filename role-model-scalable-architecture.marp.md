# Ролевая модель WOzYm - AI платформа продаж Cabinet

Масштабируемая модель доступа для команды, подключений, аналитики и агентного слоя

Phase 2 planning

---

## Контекст из WOzYm - AI платформа продаж wiki

- В WOzYm - AI платформа продаж есть личный кабинет, счета, аккаунт, API-токен и раздел "Команда и доступы".
- На тарифах бизнес-уровня подпиской можно пользоваться вместе с сотрудниками.
- Кабинетом WB могут пользоваться несколько сотрудников в рамках одной подписки.
- Основной пользователь может делиться доступом к подключению.
- Доступ к подключению может быть полным или частичным.
- Частичный доступ ограничивается брендами и категориями.
- Для брендов и категорий отдельно настраиваются просмотр и редактирование.
- В истории запросов отображается email пользователя, выполнившего действие.

---

## Вывод по референсу

Простого набора ролей недостаточно.

Нужна гибридная модель:

- `RBAC`: базовая роль пользователя в команде.
- `ReBAC`: связь пользователя с командой, подпиской, подключением.
- `ABAC`: ограничения по атрибутам данных: marketplace, brand, category, connection.
- `Audit`: фиксирование действий для лимитов, расследований и поддержки.

---

## Цели модели

- Безопасно приглашать сотрудников.
- Разделять владельца, администратора, аналитика, оператора и наблюдателя.
- Давать доступ к конкретным кабинетам и API-токенам.
- Ограничивать доступ менеджеров по брендам и категориям.
- Масштабировать модель под WB, Ozon, финансы, рекламу, agent tools.
- Не переписывать авторизацию при росте продукта.

---

## Основные сущности

- `User`: личность и учетные данные.
- `Team`: рабочее пространство компании.
- `TeamMember`: членство пользователя в команде.
- `Role`: роль пользователя внутри команды.
- `Permission`: атомарное действие.
- `MarketplaceConnection`: подключение WB/Ozon.
- `ConnectionAccess`: доступ пользователя к подключению.
- `AccessScope`: ограничения по брендам, категориям и операциям.
- `AuditEvent`: журнал действий.

---

## Базовые роли

Клиентские роли внутри `Team`:

| Роль | Назначение |
|---|---|
| `OWNER` | Владелец компании, подписки, команды и подключений |
| `ADMIN` | Управляет операционными настройками и сотрудниками |
| `MANAGER` | Работает с подключениями, себестоимостью, синками |
| `ANALYST` | Читает аналитику, делает выгрузки, строит отчеты |
| `VIEWER` | Только просмотр разрешенных разделов |
| `AGENT` | Сервисная роль для LangChain/tool calls |

---

## Платформенные роли

Платформенные роли не являются членами клиентской команды.

| Роль | Назначение |
|---|---|
| `PLATFORM_ADMIN` | Администратор платформы, полные права на систему |
| `SUPPORT_ADMIN` | Руководитель поддержки, управление обращениями и support-процессами |
| `SUPPORT_SPECIALIST` | Специалист поддержки, ограниченная диагностика и коммуникации |

Эти роли работают в отдельном ЛК с другой навигацией, аудитом и политиками.

---

## Почему платформенный слой отдельный

Team roles отвечают за доступ клиента к своим данным.

Platform roles отвечают за эксплуатацию продукта:

- поддержка пользователей;
- диагностика ошибок;
- проверка статусов подключений;
- управление обращениями;
- операционный аудит;
- административные действия платформы.

Смешивание этих ролей создаст риск случайного доступа к данным клиентов.

---

## Почему нужен OWNER отдельно

`OWNER` нельзя сводить к `ADMIN`.

Только владелец:

- управляет подпиской и счетами;
- видит API-токены аккаунта;
- передает владение;
- удаляет команду;
- меняет security-sensitive настройки;
- назначает второго владельца, если это будет разрешено политикой.

---

## Матрица верхнего уровня

| Действие | OWNER | ADMIN | MANAGER | ANALYST | VIEWER |
|---|---:|---:|---:|---:|---:|
| Управление командой | yes | yes | no | no | no |
| Подписка и счета | yes | optional | no | no | no |
| Создание подключений | yes | yes | optional | no | no |
| Управление доступом к подключению | yes | yes | no | no | no |
| Синхронизация данных | yes | yes | yes | no | no |
| Импорт себестоимости | yes | yes | yes | optional | no |
| Аналитика | yes | yes | scoped | scoped | scoped |
| Экспорт | yes | yes | scoped | scoped | optional |

## Доступ к подключению

`ConnectionAccess` отвечает на вопрос:

Может ли пользователь работать с конкретным WB/Ozon подключением?

Режимы:

- `NONE`: доступа нет.
- `FULL`: полный доступ к подключению.
- `SCOPED`: доступ ограничен атрибутами.
- `READ_ONLY`: только просмотр.
- `DISABLED`: доступ был выдан, но временно отключен.

---

## Частичный доступ

Частичный доступ моделируется через `AccessScope`.

Атрибуты scope:

- `marketplace`: `WB`, `OZON`.
- `connection_id`.
- `brand_id` или `brand_name`.
- `category_id` или `category_path`.
- `can_view`.
- `can_edit`.
- `can_export`.
- `valid_from`, `valid_until`.

---

## Пример сценария

Менеджер работает только с брендом `Brand A` и категорией `Обувь`.

Результат:

- в аналитике видит только товары этого scope;
- может редактировать себестоимость только этих товаров;
- экспорт содержит только разрешенные строки;
- agent tools получают тот же ограниченный context;
- audit фиксирует каждое действие с user/team/connection/scope.

---

Примеры:

- `platform.settings.manage`

## Platform Console

Отдельный ЛК для платформенных ролей:

- список пользователей;
- список команд;
- статус подписок;
- статусы подключений;
- очередь обращений;
- история действий поддержки;
- системный аудит;
- диагностические панели;
- later: object-level access grants.

Доступ к данным клиента по умолчанию запрещен, кроме явно разрешенных операций.

---

## Поддержка и доступ к объектам

Права поддержки на конкретные объекты будут отдельным слоем.

Будущий механизм:

- временный grant;
- конкретный объект: team, connection, ticket, sync job;
- reason/comment;
- срок действия;
- approval flow;
- обязательный audit trail;
- запрет массового экспорта без отдельного разрешения.

---

## Масштабирование прав

Роли не должны хранить бизнес-логику в коде.

Правильная схема:

- роль дает набор permissions;
- permission проверяется policy engine;
- resource-level scope фильтрует данные;
- feature flags включают новые модули без миграции ролей;
- тарифные ограничения проверяются отдельно от прав пользователя.

---

## Слой подписки

Подписка не равна роли.

Подписка определяет:

- доступные модули;
- лимиты;
- количество кабинетов;
- ограничения на сотрудников;
- доступность API;
- доступность agent layer.

Роль определяет:

- что конкретный пользователь может делать внутри доступных модулей.

---

## Слой данных

Все продуктовые таблицы должны иметь:

- `team_id`;
- `connection_id`, если данные относятся к кабинету;
- marketplace-specific идентификаторы;
- поля для brand/category scope;
- timestamps;
- source sync metadata.

Это позволит фильтровать данные на уровне SQL, API и agent tools.

---

## API Guard Pattern

Каждый endpoint проходит три проверки:

1. Auth: пользователь вошел.
2. Team access: пользователь состоит в команде.
3. Authorization: role + permission + resource scope.

Пример:

`authorize(user, "costs.import", team, connection)`

После этого запросы к БД добавляют scope-фильтр.

В ЛК нужны разделы:

- `Команда и доступы`.
- `Роли`.
- `Подключения`.

## Управление доступом к подключению

Экран подключения:

- список пользователей;
- режим доступа: полный, частичный, просмотр, отключен;
- быстрый поиск по email;
- дата отключения;
- настройки scope;
- бренды и категории с флагами просмотра и редактирования;
- аудит последних изменений.

---

## Agent Layer

LangChain/tools должны использовать ту же модель прав.

Правила:

- агент действует от имени пользователя или сервисной роли;
- каждый tool call получает `team_id`, `user_id`, `permissions`, `scope`;
- tools не читают данные напрямую без policy check;
- audit фиксирует prompt intent, tool name, resource, result status;
- dangerous tools требуют дополнительного approval.

---

## Риски

- Слишком простая RBAC-модель быстро сломается на брендах и категориях.
- Проверки только во frontend не защищают данные.
- Scope-фильтрация после выборки создает риск утечки.
- Agent tools без единого policy layer обойдут ограничения UI.
- Billing/roles смешивать нельзя: это разные домены.

---

## Рекомендуемый путь

1. Сначала ввести `Team` и `TeamMember`.
2. Добавить роли и permission catalog.
3. Защитить все текущие API через team guard.
4. Добавить `ConnectionAccess`.
5. Ввести `AccessScope` для брендов и категорий.
6. Добавить UI управления командой.
7. Расширить audit.
8. Подключить agent tools к тому же policy layer.

---

## Phase 2 Acceptance

Готово, когда:

- владелец может пригласить сотрудника;
- сотрудник входит своим email/phone + password;
- пользователь работает только в разрешенной команде;
- аналитика фильтруется по team + connection + scope;
- владелец выдает полный или частичный доступ к подключению;
- export не содержит запрещенных строк;
- audit показывает кто и что сделал;
- agent endpoint не обходит ограничения.
