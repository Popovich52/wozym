# Ozon API для WOzYm - AI платформа продаж

## Короткая схема данных и хранения

Дата: 2026-05-30  
Источники: `docs.ozon.com`, `wiki.wozym.io`

---

# Два канала интеграции

## 1) Seller API (операционный контур магазина)
- хост: `api-seller.ozon.ru`
- auth: заголовки `Client-Id` + `Api-Key`
- ключ с ролью доступа, срок: 6 месяцев

## 2) Performance API (реклама)
- хост: `api-performance.ozon.ru`
- auth: `client_id` + `client_secret` -> `access_token (Bearer)`
- суточный лимит: до `100000` запросов

---

# Какие данные получаем: Seller API

## Основные домены данных
- каталог: категории, атрибуты, карточки, медиа, сертификаты
- цены и остатки: цены, скидки, остатки по складам
- заказы и логистика: FBO/FBS/rFBS/FBP, отправления, поставки
- возвраты и отмены: заявки, статусы, действия
- финансы и аналитика: транзакции, cashflow, аналитические отчеты
- коммуникации и качество: чаты, отзывы, рейтинги

---

# Какие данные получаем: Performance API

## Основные домены данных
- кампании: список, статусы, объекты продвижения
- статистика: дневная, по расходам, по заказам, по товарам
- поисковое продвижение: фразы, ставки, конкурентность
- управление рекламой: запуск/остановка кампаний, создание кампаний CPC
- лимиты и состояние отчетов: UUID-статусы, очереди выгрузок

---

# Что можно делать ключами на площадке

## Seller API key
- не только читать, но и изменять данные магазина (зависит от роли ключа)
- загружать/обновлять товары, цены, остатки
- управлять заказами, отгрузками, возвратами
- отправлять сообщения в чатах, работать с промо и отчетами

## Performance credentials
- получать рекламную статистику
- управлять рекламными кампаниями и ставками
- запускать и останавливать продвижение

# Модель хранения в нашей системе

## Разделяем на 3 слоя
- `connections` (настройки доступа): кто владеет подключением, статус, срок ключа
- `raw_events` (сырые ответы): полный JSON ответа Ozon + метаданные запроса
- `core marts` (нормализованные витрины): товары, цены, остатки, заказы, финансы, реклама

## Ключевые принципы
- идемпотентность загрузок (`external_id` + `updated_at`)
- версионирование фактов по дате/часу
- трассировка: из какой ручки и какой синхронизацией получены данные

# Хранение ключей: рекомендованный вариант

## Рекомендуется
- хранить секреты в шифрованном виде (KMS/Vault/pgcrypto)
- в UI показывать только маски (`****`)
- хранить `expires_at`, `last_check_at`, `last_success_at`
- audit log на чтение/изменение credentials

## Если нужен открытый вид (бизнес-требование)
- ограничить доступ только владельцу/админу команды
- запретить экспорт и массовую выгрузку секретов
- обязательный аудит каждого просмотра ключа
- отдельный флаг риска в политике безопасности

---

# Привязка к пользователю и правам

## Как связать корректно
- владелец: `created_by_user_id`
- область данных: `team_id` + ACL на `connection_id`
- шаринг: отдельная таблица прав (`read`, `manage`, `sync`, `view_secret`)

## Важно
- право `view_secret` выдавать отдельно от `manage_connection`
- для операторов и аналитиков оставлять доступ без просмотра секретов

---

# Проверки и эксплуатация

- health-check подключения: Seller `/v1/roles`, Performance token endpoint
- авто-алерт до истечения ключа (например, `T-14/T-7/T-1`)
- backoff/retry + защита от rate limit
- дедупликация sync jobs и блокировка параллельных тяжелых выгрузок

---

# Вывод для реализации

- Ozon закрывает оба нужных контура: операционный (Seller) и рекламный (Performance)
- для аналитики WOzYm - AI платформа продаж достаточно хранить:
  - сырые ответы для воспроизводимости
  - нормализованные витрины для быстрых отчетов
- открытое хранение ключей возможно технически, но безопаснее оставить только как исключение с жестким ACL и аудитом
